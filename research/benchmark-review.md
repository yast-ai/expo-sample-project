# Benchmark review

Raw Android EAS preview builds with six Gradle workers and a 4 GiB heap are the provisional default on 8 CPU / 16 GB VMs. Native baseline cold/warm times were 392.986/235.989 seconds, compared with 460.808/256.288 seconds at eight workers. These are observed comparisons, not a universal speed guarantee.

Docker now has successful signed preview APKs. At six workers and 4 GiB, a shared-cache mount recorded 442.387/255.899/239.838 seconds for cold/warm/warm2. The ccache lane recorded 456.943/168.128/254.058 seconds. The isolated 168-second improvement did not repeat. Verify generated compiler launchers and per-build ccache counter deltas before attributing a gain to ccache. Docker can also incur swap pressure, including roughly 2 GiB in one warm run. A stable OOM counter does not prove absence of memory pressure.

The six-worker 6 GiB heap lane recorded 510.837/264.257/242.512 seconds and reached 14.50 GiB used memory in its first warm run. It is not the demonstrated winner. Earlier 3/4 GiB lane failures happened in SDK or launcher setup and do not establish heap-performance differences. The subsequent private retry uses six workers, 4 GiB and exact idle-daemon cleanup; private source stays off public repositories.

The reusable v3 template includes Android platform 36 and build-tools 35/36, CMake 3.22.1 and 3.30.5, JDK 17, Node/Bun, Docker, and public dependency downloads. It excludes project code, credentials, signing material and populated task/compiler caches. Per-build scripts explicitly enable Gradle caching/parallelism with six workers and a 4 GiB heap.

The earlier Hello v2 restore test recorded 122/66 seconds with fresh EAS directories but retained public Maven/npm downloads. Gradle task output caching was disabled, and both runs had zero FROM-CACHE tasks. Label the first run template-prewarmed; this pair measures dependency/tool warming rather than Gradle task-cache reuse. A controlled follow-up should populate task caches and collect two warm repetitions on identical source and toolchain.

Full Gradle task durations overlap. Docker native warm2 had 772.79 seconds of summed task work within a 240.59-second Gradle build. Its app arm64 CMake configuration task occupied 109.39 seconds, making CMake logs and repeated setup a higher-value investigation than another unstructured worker sweep. Task start/end telemetry lets the report show both work totals and merged occupied wall intervals.

Artifacts upload directly from the VM to Cloudflare R2 through the official Convex component. The stable download endpoint redirects to a signed R2 URL. Request-to-artifact timing includes metadata publication; artifacts uploaded retrospectively are excluded from end-to-end comparisons. The public sample action intentionally has no auth and is restricted to permitted yast-ai HTTPS repositories.

The prepared installer now also requests Android platform 35 for older pinned apps and platform/build-tools 37 for SDK 58. The private cold log confirms Gradle 9.4.1 installed platform 37 and build-tools 37.0.0 during compilation. Baking these public tools into the next template will remove that installation from future requests. The v4 snapshot now contains these tools. An actual restored-worker build is still pending; the Hello check ran on its already prepared source VM.

Private SDK 58 cold builds completed in 961 seconds with a 4 GiB heap and 1,060 seconds with 3 GiB. Both warm attempts failed with a disappearing Gradle daemon near Metro startup. An OOM kill was recorded on each VM, but the kernel victim was not retained. Two older Kotlin daemons remained resident, consuming about 1.65 GiB combined RSS before a third warm compiler daemon appeared. The next controlled retry retains six workers, a 4 GiB Gradle heap and a 1 GiB Kotlin heap while stopping the exact idle compiler daemon processes between builds. It preserves filesystem caches. If that still fails, cap Metro at two workers in a separate experiment before reducing Gradle workers. This is a hypothesis to test, not a measured speedup.

A targeted next native experiment would persist app CMake buildStagingDirectory outside the fresh EAS working directory, under a project/source/lock/toolchain/ABI fingerprint. The existing Docker runner keeps absolute source paths stable but deletes .cxx staging on every fresh build. This does not restore node_modules staging automatically. Keep preview APK and all default ABIs unchanged; invalidate on any fingerprint change. Android documents that the staging directory holds Ninja files and should persist outside temporary build directories: https://developer.android.com/reference/tools/gradle-api/7.2/com/android/build/api/dsl/Cmake . This change is not yet benchmarked.

The private project explicitly enables release minification and resource shrinking. Its latest cold R8 task took 176.905 seconds and averaged 76.9% VM CPU, with no other recorded Gradle task overlapping. Raising Gradle workers does not directly raise R8's thread count. The matched warm build must finish before the separate R8-off comparison. Disabling R8 also changes output optimization and is not a cache speedup. SDK behavior should be checked against resolved project configuration. Source: https://developer.android.com/build/r8-execution-profiles .

The first v4 template upgrade failed validation because the SDK37 package directory lacked aapt2 after sdkmanager returned. That VM was stopped and deleted before any app or credential transfer. The prepared installer now validates the tool binary and can recover it from the official Google Linux archive, verified against the published repository checksum. This fallback has been archive-validated locally; a fresh VM restore check is still pending.

Astra reviewed SDK58 private logs: the final app createBundleReleaseJsAndAssets task took 42.4/45.8 seconds (4/3 GiB), while its Metro Bundled line reported 11.592/11.519 seconds. An earlier EAS eager app pass reported 10.097/10.805 seconds. Widget tasks are distinct outputs; their displayed durations can overlap other Gradle work. A future isolated EAS_BUILD_DISABLE_BUNDLE_JAVASCRIPT_STEP=1 test can remove the early error check, but final JavaScript/Hermes bundling remains required and any cache warming effect must be measured.
