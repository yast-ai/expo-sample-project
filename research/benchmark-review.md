# Benchmark review

The completed control and JS-heavy runs used an 8 CPU and 15.62 GiB VM. No run OOMed. Six workers should remain the baseline. Eight workers did not improve cold runs and made preview warm builds slower. Production warm at eight workers was 1.4 seconds faster than six, but used 10.32 GiB and left 5.29 GiB free. The current `-Xmx4096m` Gradle and `-Xmx1024m` Kotlin limits fit these measurements.

The JS-heavy registry has 100 imported screen modules, and its check script verifies the count and every registry import string. Its build scripts use the preview APK and production AAB profiles. The Convex variant keeps its public configuration and deployment URL in `READY.json`; its current build commands fetch EAS CLI with `npx`, so it does not share the local pinned CLI property used by the control and native-heavy variants.

Docker is installed in the toolchain snapshot and the daemon is usable. Version 29.7.0 ran on the same 8 CPU and 15.62 GiB VM. Image preparation took 30.2 seconds for Node 24, JDK 17, and Bun 1.4.2. The cold container build reached Gradle and used 399.22% CPU and 3.38 GiB container memory before failing. The Android SDK mount contained Build-Tools 36.0.0, while Gradle also requested 35.0.0. A read-only mount prevented its install. Docker therefore adds image preparation and mount and UID handling, and did not produce a comparable successful APK. A valid rerun needs Build-Tools 35 installed in the reusable template or a writable SDK overlay. Keep the EAS working directory fresh and describe only Bun and Gradle as warm caches.

The reusable template installer explicitly installs only Build-Tools 36.0.0. A successful raw build log shows Gradle automatically installing 35.0.0 into writable `/home/user/android-sdk`; Docker's read-only SDK bind mount made the same fallback fail. The template should include 35.0.0 for a read-only Docker SDK, or Docker must mount a writable SDK overlay.

The current direct upload path is sound for the measured APK sizes: the VM posts bytes directly to a generated Convex Storage URL, validates the returned `storageId` through `ctx.db.system.get`, and preserves timestamps before stopping the no-snapshot sandbox. Two limits matter for larger artifacts. The `curl --max-time 115` upload has no retry or resumable multipart path, so a 1 GB artifact needs more than about 9.1 MB/s sustained upload to complete. Also, `artifactReadyAt` records the HTTP response before the following metadata query and database update; it is not the full client-observable completion time. The public unauthenticated action can also trigger Boat work with the Expo token for any permitted `yast-ai` repository, so it is suitable only for the stated sample deployment.
